# 数据长期演进与版本兼容计划

宝宝记录可能需要保存十几年，数据生命周期会明显长于任何一版 APP。本项目把“原始记录可恢复”作为高于界面和统计功能的约束。

## 1. 数据原则

- 原始事件与派生结果分离：睡眠起止、奶量等原始记录永久保存；日报、趋势、待办建议可以随算法升级重新计算。
- 全局稳定 ID：记录、宝宝、家庭成员和设备都使用 UUID，不把数据库自增 ID 暴露给客户端。
- 删除使用墓碑：同步数据以 `deleted_at` 标记删除，所有设备确认后再进入归档清理流程。
- 未知字段不丢失：旧客户端读到新字段后，回写时必须保留它们。
- 时间同时保存本地时间、时区和 UTC，避免旅行、夏令时或 NAS 时区变化破坏记录。
- 每条记录保存稳定的 `time_mode`（`instant` 或 `range`）；时间段记录把“进行中”表示为缺少 `ended_at` 的正常状态，不另造不可迁移的临时类型。
- 自定义项目保存稳定的图标键、颜色键和默认 `time_mode`。界面素材可以替换，但已保存键值必须有降级图标，不能导致旧记录无法显示。
- 宝宝档案、家庭共享记录与用户偏好分离：主页快捷项和长辈模式按 `user_id` 保存，不会覆盖其他家庭成员的界面设置。
- 当前角色使用独立的本地会话键保存，角色目录和用户偏好分别版本化；清除当前会话不会删除角色的历史偏好或宝宝记录。
- 客户端每天生成一份可恢复快照，同一自然日重复备份会更新当日快照，并滚动保留最近 30 天；NAS 端使用相同保留策略执行独立服务端备份。

## 2. 三层版本号

版本号彼此独立：

- `app_version`：用户安装的 APP 版本。
- `schema_version`：本地导出包和 SQLite 数据结构版本。当前为 v3；v2 为记录和自定义项目补充稳定的 `time_mode`，v3 为每条记录补充本地日期并清理早期原型演示数据。
- `api_version`：NAS 同步协议版本，例如 `/api/v1/sync`。

服务端同步握手返回 `min_read_version`、`min_write_version` 和功能能力列表。过旧客户端可以只读导出，但不能继续写入无法安全理解的新结构。

## 3. 迁移机制

代码中的迁移注册表位于 `src/data/schema.ts`。每次结构变化只追加迁移，例如：

```text
v1 --add_timezone--> v2 --split_feeding_type--> v3
```

已发布的迁移不得修改。升级顺序为：

1. 校验剩余空间、数据版本和备份可用性。
2. 创建带校验和的加密快照。
3. 在事务或临时副本中逐版本迁移。
4. 执行记录数、外键、时间范围和校验和检查。
5. 原子切换到新数据库；失败则恢复升级前快照。
6. 保留最近若干次升级备份，用户确认正常后再清理。

## 4. 数据模型演进规则

- 新增可选字段属于向后兼容更新。
- 字段改名采用“新增字段 → 双写 → 回填 → 停止读取旧字段 → 后续版本删除”的多版本流程。
- 枚举值允许扩展，客户端必须提供“未知类型”的降级显示。
- 不直接修改历史原始记录；修正内容产生新的 revision，并保留审计信息。
- 大型媒体与结构化记录分离，数据库只保存内容哈希、元数据和对象路径。

## 5. NAS / Docker Compose 升级

- 镜像使用明确版本号，不使用不可追踪的 `latest`。
- 数据库迁移由独立的一次性 migration 容器执行。
- 更新前 backup 容器完成 PostgreSQL 和文件快照，失败则阻止升级。
- API 通过健康检查后才切换反向代理；旧镜像至少保留一个回滚周期。
- WebDAV 备份包含 manifest、schema 版本、文件校验和与加密参数。

## 6. 测试与发布门槛

每个迁移版本必须包含：

- 从所有仍受支持旧版本升级的测试样本。
- 重复运行迁移的幂等性测试。
- 中途断电/进程终止后的恢复测试。
- Android、Web、NAS 不同版本组合的同步契约测试。
- 导出后重新导入的数据等价性测试。

正式发布前先对匿名副本执行迁移演练，再逐步扩大更新范围。

## 7. 用户可控与退出能力

用户始终可以导出不依赖本 APP 的 JSON 和 CSV。JSON 导出包含完整版本化数据和审计信息；CSV 用于阅读和分析。任何服务停止维护时，都必须提供离线读取工具和完整迁移文档。
